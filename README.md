# 知识库条目质量治理工具

一个可复用的 Streamlit 知识库“体检”工具。业务方可以在页面上传或粘贴当前业务规则摘要和 FAQ，点击一次即可查看问题分布、问题条目、检测依据、治理建议，并下载 Markdown、CSV、HTML 报告。

## 快速运行

```bash
cd project
pip install -r requirements.txt
streamlit run app.py
```

打开终端显示的本地地址即可使用。项目目录中的 `task6_business_context.md` 和 `task6_kb_articles.json` 会作为默认演示数据自动加载。

## 页面使用

1. 上传或粘贴业务规则摘要。
2. 上传或粘贴 FAQ 数组。支持 JSON、CSV、TSV、Excel。
3. 选择 `Mock（本地演示）` 或 `LLM（真实 API）` 模式。
4. 点击“开始质量体检”。
5. 在报告区查看问题，并下载报告。

FAQ 最少需要 `id`、`question`、`answer`、`category` 字段；`created_at` 和 `updated_at` 用于追溯。

## 问题分类体系

| 类型                    | 判定方式                                                     | 影响                                             | 默认动作               |
| ----------------------- | ------------------------------------------------------------ | ------------------------------------------------ | ---------------------- |
| 内容过时 / 业务规则冲突 | 将答案中的时效、支付、发票、会员、优惠、客服等事实与当前规则摘要比对 | 可能对用户作出错误承诺，引发退款、投诉或客服成本 | 立即修改               |
| 条目重复或相互矛盾      | 对问题做近似匹配；相似问题若答案不同则标记冲突               | 检索命中不稳定，机器人可能随机返回不同政策       | 合并并保留唯一权威条目 |
| 答案缺失                | `answer` 为空                                                | 用户得到空响应，等同于知识缺口                   | 补充或明确“不支持”     |
| 答案可执行性不足        | 操作类问题缺少入口、步骤、条件或替代渠道                     | 用户知道结论却无法完成操作                       | 补充步骤和异常处理     |

工具还会把未覆盖的高价值主题输出为“覆盖缺口”，例如投诉/申诉、隐私、保修和账号注销说明。

## 检测方法

检测引擎位于 `../project/kb_quality.py`，与页面解耦，后续可以复用到定时任务、API 或 CI 检查。

- **结构检查**：校验输入格式、必需字段和空答案。
- **规则比对**：从 Markdown 规则摘要提取退货期限、发货时效、支付方式、发票类型、会员门槛、优惠券叠加和客服时间等事实，再与答案中的事实比对。
- **近重复检测**：对问题做清洗后使用字符相似度识别近重复和相互矛盾的答案。
- **可执行性检查**：检查操作类回答是否提供页面入口、动作动词、条件或人工渠道。
- **治理建议**：按问题类型和风险生成“修改、合并、删除、补充、新增”建议，并将高风险项目排序到前面。
- **LLM 兼容**：兼容常见供应商返回的 `factual_inaccuracy`、`incorrect_info`、`outdated_info`、`empty_answer`、`content_conflict`、`missing_information` 等问题类型别名，并兼容用 `description` 代替 `summary/evidence` 的结果格式，统一映射到本系统分类。

## AI 工具使用情况

默认是 **Mock 模式**：不调用外部 API，使用本地确定性规则完成可复现的扫描，方便离线运行和演示，也避免业务数据外传。

**LLM 模式会调用真实 API。** 选择 LLM 后，页面侧边栏会显示 API Key、API 地址输入框和模型下拉框；配置只保存在当前 Streamlit 浏览器会话内，不写入系统环境变量、报告或项目文件。工具先调用 OpenAI-compatible 的 `GET /models` 获取可选模型，再调用 `POST /chat/completions`，把业务规则摘要和 FAQ 一次提交给选中的模型，优先要求模型按 JSON Schema 返回问题类型、严重度、证据、治理建议和关联条目，并把 `article_id` 限制为本次输入中的真实 FAQ ID；如果服务端返回不支持 `response_format=json_schema` 的 400/422，工具会自动重试 `json_object` 模式并继续校验 JSON。若模型仍返回空 ID 或不存在的 FAQ ID，工具会自动发起一次纠正请求，要求将无法关联 FAQ 的内容放入 `coverage_gaps`；纠正后仍非法的结果才会被安全忽略。确定性规则始终先执行，LLM 只负责语义复核和补充；所有模型结果都会校验 FAQ ID、问题类型和严重度后再合并。

启动页面后按以下步骤配置：

1. 在侧边栏将检测模式切换为 `LLM（真实 API）`。
2. 填写当前服务的 `API Key`，密钥输入框为密码类型，不会显示明文。
3. 填写 `API 地址`；地址需要支持 OpenAI-compatible 的 `/models` 接口。
4. 系统自动获取可用模型列表，在 `模型名称` 下拉框中选择模型；接口变更后可点击“重新获取模型列表”。
5. 上传或粘贴业务规则与 FAQ，点击“开始质量体检”。

勾选“记住 LLM 配置”后，API Key、API 地址和模型会保存到当前浏览器的 localStorage；取消勾选会清除已保存配置。localStorage 中的 Key 以浏览器本地明文形式保存，仅建议在个人设备使用。模型返回缺少 FAQ ID 等非法项时，工具会先自动纠正一次；仍无法关联的结果会被忽略，并在页面“查看被忽略的 LLM 原始结果”区域及下载报告中保留序号、原因和原始 JSON。未填写 API Key、服务超时、HTTP 错误或模型返回整体结构非法时，页面会停止本次扫描并展示中文错误，不会把不完整结果当成成功结果。生产使用仍应增加数据脱敏、访问控制、重试/限流、成本预算和人工审核；模型输出不能绕过确定性业务规则。

## 治理报告摘要（示例数据）

本附件包含 40 条 FAQ；当前 Mock 扫描结果为 10 条问题条目、13 个高优先级问题、4 个覆盖缺口，问题分布为 12 个规则冲突、1 个重复冲突、2 个空答案。工具会重点标记退货运费、发货时效、货到付款、纸质发票、会员权益、优惠券叠加、在线客服时间等与当前规则不一致的条目，同时标记空答案、相互矛盾的退货政策，以及商品保修、账号注销、投诉/申诉和隐私等覆盖缺口。

报告会展示：

- 总条目数、问题条目数、高风险问题数、覆盖缺口数。
- 问题类型分布和优先处理建议。
- 每条问题的原答案、检测依据、关联条目和具体治理动作。
- 可下载的 Markdown、CSV 和自包含 HTML 报告。
